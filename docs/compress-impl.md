方案的上下文压缩机制是一套分层递进、预防为主、反应为辅的工程体系。其核心目标是在不中断用户工作流的前提下，用最低成本维持上下文在窗口安全线内，同时确保压缩后 Agent 不会"失忆"。

以下从原理拆解到复刻方案完整梳理。

---

一、机制原理拆解

1. 整体哲学：漏斗式分层防御

整个压缩体系按成本从低到高、侵入性从弱到强排列，形成一条流水线。每一层只处理上一层剩下的问题，避免"杀鸡用牛刀"。

预防层（API 调用前，每轮检查）：
- 工具结果预算控制：单条结果过大时直接截断或外存，保留预览
- 老消息剪裁：对极旧消息直接丢弃
- 微压缩：清空旧工具输出的详细内容，仅保留语义占位符
- 上下文折叠：后台异步对旧消息段生成摘要，主对话无阻塞
- 自动压缩：接近窗口上限时，调用独立会话生成全量结构化摘要

反应层（API 调用失败后）：
- 紧急折叠提交：把后台已生成但未确认的折叠摘要立即生效
- 应急压缩：收到"提示词过长"错误后，紧急调用摘要服务
- 剥洋葱式截断：若摘要服务仍报错，逐次舍弃最旧的消息组重试

兜底：
- 连续失败断路器：若压缩连续失败达到阈值，永久停止尝试，避免无限浪费资源

2. 动态阈值设计

不是等窗口塞满才行动，而是提前预留安全空间。

- 摘要预留：为压缩输出预留固定额度，防止"用来压缩的工具本身没地方放"
- 缓冲带：在达到窗口硬上限前再预留一段缓冲，确保压缩过程中有"转身的空间"
- 有效可用窗口 = 模型标称窗口 - 摘要预留 - 缓冲带

例如 200K 窗口模型，实际在约 167K 时就会触发自动压缩，而非拖到 200K。

3. 微压缩：无成本日常清理

这是最轻量、每轮必做的操作，不调用任何模型，纯规则处理。

核心策略：
- 维护一个可压缩工具白名单（如文件读取、Shell 执行、搜索、网页抓取、编辑等）
- 对历史轮次中这些工具的大段输出，清空具体内容，替换为极简占位标记
- 不在白名单中的工具（如子 Agent、技能、MCP 等）保留原样，避免破坏复杂状态

效果： 消息条数不变，结构不变，但旧内容体积骤降，且保留了"这里曾发生过什么"的语义线索。

4. 上下文折叠：后台异步摘要

这是一种渐进式、非阻塞的压缩手段。

生命周期：
1. 后台孵化侧链会话，传入一组旧消息生成摘要
2. 摘要进入暂存区，等待确认主对话近期未引用这些消息
3. 确认安全后提交为只读记录
4. 向主模型发送消息时，动态将原消息替换为摘要占位符

优势： 用户无感知，不增加当前轮次的延迟，且保留了原文的检索能力。

5. 自动压缩：Fork 会话与缓存复用

当微压缩和折叠仍无法遏制上下文膨胀时，触发全量摘要。

关键设计：
- 创建一个与主会话隔离的 Fork 会话，由它负责阅读全部历史并生成结构化摘要
- Fork 会话共享主会话的 Prompt Cache，避免重复上传系统提示词，显著降低成本
- 摘要生成后，整条历史被替换为一条精简摘要消息

预处理管线（发送给 Fork 前）：
- 剔除图片、PDF 等大媒体，替换为文本标记，防止"用来压缩的请求先超限"
- 删除会被自动重新注入的附件（如技能发现列表），避免重复导致幻觉
- 规范化消息格式

6. 压缩方向：保前还是保后

全量压缩支持两种策略，本质是缓存成本与信息新鲜度的权衡：

- 保前策略：压缩后半段，保留前半段。系统提示词等静态前缀不动，Prompt Cache 持续命中，成本最低
- 保后策略：压缩前半段，保留后半段。缓存失效，但最新对话完整保留，信息损失最小

7. 状态重启点补偿：压缩后不"失忆"

这是整个机制中最关键的一环——压缩不是简单丢弃，而是精准重建工作现场。

压缩完成后，系统会主动将以下状态重新注入上下文：
- 当前正在查看的文件内容（带截断上限，避免回注后再次超限）
- 正在执行中的计划（Plan）和技能（Skill）
- 待处理的工具协议变更
- 所有激活的外部工具与服务的完整声明

最终上下文结构：
系统边界 + 历史摘要 + 当前文件片段 + 进行中的计划 + 激活的工具声明

这让模型感觉"桌面刚被整理过，但手边的资料和工具都在原位"。

8. 应急与容错

- 剥洋葱截断：若全量摘要请求本身超限，从最旧的消息组开始逐批舍弃，最多重试数次，以"有损"换"可用"
- 记忆压缩回退：若调用模型生成摘要失败，直接使用后台渐进提取的 Session Memory 作为摘要，零成本
- 断路器：统计发现部分会话会因极端情况无限触发压缩失败，因此设置连续失败上限，达到后直接跳过，避免资源黑洞

---

二、复刻方案

基于上述原理，以下是一套可直接落地的工程复刻方案。

架构设计

```
用户消息流
    │
    ▼
┌─────────────────────────────────────┐
│  预防层（每轮 API 调用前执行）        │
│  ① 工具结果预算控制 → 截断/外存大结果 │
│  ② 老消息剪裁 → 丢弃超期消息         │
│  ③ 微压缩 → 清空旧工具输出为占位符   │
│  ④ 上下文折叠 → 后台异步摘要旧段落   │
│  ⑤ 自动压缩 → Fork 会话全量摘要      │
└─────────────────────────────────────┘
    │
    ▼
  调用 LLM API
    │
    ▼
┌─────────────────────────────────────┐
│  反应层（API 调用失败后执行）          │
│  ⑥ 紧急折叠提交 → 立即生效暂存摘要    │
│  ⑦ 应急压缩 → 紧急生成摘要            │
│  ⑧ 剥洋葱截断 → 逐批舍弃旧消息重试   │
└─────────────────────────────────────┘
```

第一层：工具结果预算控制

实现要点：
- 为每个工具的输出设置单条上限（如 8K tokens）
- 超限后，将完整结果写入本地缓存或文件系统，消息中只保留前 N 行预览 + 外部引用标记
- 对图片、PDF 等二进制内容，一律转为文本占位符

第二层：老消息剪裁

实现要点：
- 设定一个消息条数或 token 数的硬边界
- 超出部分直接从头部删除
- 可保留最近 N 条文本消息的底线，避免删成空对话

第三层：微压缩

实现要点：
- 定义可压缩工具白名单，覆盖所有可能产生大段输出的工具
- 遍历历史消息，识别工具调用结果块
- 对非当前轮次的旧结果，将内容替换为固定格式占位符（如 `[先前执行了 Bash 命令，输出已归档]`）
- 保留工具名称、执行状态、时间戳等元信息

第四层：上下文折叠

实现要点：
- 将历史消息按逻辑段（如每 3-5 轮对话）分组
- 当主对话进行时，后台启动独立任务，对最旧的未折叠组调用轻量模型生成摘要
- 摘要进入"暂存-提交"两阶段：先生成，等待确认主对话近期未引用该组内容后，再标记为已提交
- 消息投影层负责在发送给主模型时，将已提交组替换为 `<collapsed>摘要内容</collapsed>`

第五层：自动压缩

实现要点：

阈值配置：
- 有效窗口 = 模型窗口 - 摘要输出预留（建议 15K-20K）
- 触发阈值 = 有效窗口 - 缓冲带（建议 10K-15K）

Fork 会话：
- 创建独立会话实例，传入当前完整历史
- 复用主会话的系统提示词缓存（若 API 支持 Prompt Cache）
- 要求 Fork 会话输出结构化摘要（如 `<analysis>关键决策</analysis> + <summary>事件脉络</summary>`）

预处理：
- 发送前剔除所有图片、文档附件
- 删除会被自动重新注入的动态附件
- 统一消息格式

压缩方向选择：
- 默认优先"保前"，以维持缓存命中
- 当最近轮次包含关键执行计划时，切换为"保后"

第六层：状态补偿

实现要点：
压缩完成后，在摘要消息之后立即插入：
1. 文件补偿：当前通过工具打开且未关闭的文件路径 + 内容前 N 行
2. 计划补偿：进行中的计划 ID + 目标 + 当前步骤
3. 技能补偿：激活的技能名称 + 参数状态
4. 工具声明补偿：所有可用工具的完整 Schema 声明（确保模型继续知道能调用什么）

第七层：应急与容错

实现要点：
- 剥洋葱截断：将消息按轮次分组，从头部开始每次舍弃 20% 最旧内容，重试摘要请求，最多 3 次
- 记忆回退：维护一个后台 Session Memory 缓冲区，在模型摘要失败时，直接用已有记忆替代历史消息
- 断路器：维护失败计数器，连续失败 3 次后，该会话永久跳过自动压缩，仅依赖微压缩和剪裁

关键配置参数建议

参数	200K 窗口模型	1M 窗口模型	
摘要输出预留	20K	20K	
缓冲带	13K	13K	
触发阈值	167K	967K	
微压缩白名单	Read/Bash/Grep/Glob/WebSearch/Edit/Write	同上	
折叠组大小	3-5 轮	3-5 轮	
记忆回退保留最近消息	最少 10K tokens / 5 条	最少 10K tokens / 5 条	
连续失败上限	3 次	3 次	

工程落地建议

1. 监控先行：上线前必须统计每层的触发频率、实际节省 token 数、压缩失败率，用于动态调参
2. 缓存即成本：若所用 API 支持 Prompt Cache，务必在 Fork 会话中复用主会话缓存，这是成本优化的核心
3. 渐进启用：先上线微压缩和预算控制（零风险），再逐步开启折叠和自动压缩
4. 用户透明：在 UI 层提供"上下文已整理"的轻提示，避免用户因历史突然变短而产生困惑
5. 测试极端场景：模拟单条输入就超过触发阈值的场景，确保系统不会陷入"想压缩但连压缩的空间都没有"的死锁

---

这套方案的核心价值在于用规则解决 80% 的问题，用模型解决 20% 的瓶颈，用状态补偿保证连续性，在成本、延迟和上下文完整性之间取得平衡。
